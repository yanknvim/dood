# Context

タイトルバーがウィンドウの上端を常に占有し、常に最前面で使う小さなスクラッチパッドには
重い。macOS の信号機と Linux の WM の枠をそれぞれ活かす案もあったが、
「Linux でも macOS でもタイトルバーをなくす」という要望があった。

枠を消すと、移動・閉じる・最小化の手段が OS から提供されなくなる。
キャンバスは全面ドラッグで描くため、ウィンドウの移動と描画が競合してはいけない。

# Decision

1. すべてのプラットフォームで `ViewportBuilder::with_decorations(false)` を使い、
   タイトルバーを描かせない。
2. ウィンドウの移動は、ツールバーの余白（ボタンの外）のドラッグで行う。
   `Response::drag_started()` で `ViewportCommand::StartDrag` を送る。
   ドラッグ領域はボタンより先に登録し、ボタン側もドラッグを受け取る
   （`Sense::click_and_drag`）ことで、ボタン上からのドラッグでウィンドウが動かないようにする。
3. 閉じる操作は `⌘W`（Linux は `Ctrl+W`）に割り当て、`ViewportCommand::Close` を送る。
   macOS の `⌘Q`、Linux の `Alt+F4` もそのまま使える。
4. タイトル文字列 `dood` は Dock / タスクバー表示のために残す。
5. ウィンドウのリサイズは OS / WM のエッジ操作に任せ、アプリ内につまみは置かない。

不採用: macOS だけ fullsize content view とタイトル非表示で信号機を残す案
（Linux と枠の構成が分かれ、信号機のぶんツールバー左に余白が要る）、
タイトル文字だけ消してバーを残す案（高さ約 28pt が残る）、
閉じるボタンをツールバーに足す案（ボタンがさらに増え、キーボードで足りる）、
macOS の `movableByWindowBackground` に任せる案（キャンバスのドラッグ描画と競合する）。

# Consequences

## Pros

- タイトルバーの約 28pt がなくなり、キャンバスが広く、枠のない見た目になる。
- macOS と Linux で同じ構成になる。
- 常に最前面の小さなウィンドウとして使いやすい。

## Cons

- 閉じる・最小化・ズームのボタンが無い。閉じるはキーボード（`⌘W` / `Ctrl+W`、
  `⌘Q` / `Alt+F4`）か OS のウィンドウ一覧から行う。
- ウィンドウの移動はツールバーの余白ドラッグだけで、ボタン上からは動かない。
- リサイズのつまみが見えず、OS / WM のエッジ操作に依存する。
- 枠が無いぶん、影や角丸は OS の扱いに依存する。
