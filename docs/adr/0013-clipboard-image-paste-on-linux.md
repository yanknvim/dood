# Context

Linux に移植した後、画像のペーストが動かなくなった。原因は複数ある。

- egui-winit は `⌘V` でクリップボードにテキストがあると `Event::Paste(text)` だけを出し、
  `Event::PasteImage` を出さない。テキストは画像より常に優先される。
- Linux のファイルマネージャは、コピーした画像ファイルを画像データではなく
  `text/uri-list`（`file:///path/to/image.png`）として置く。これは `text/*` なので
  クリップボードのテキストとして取得され、画像としては取り込まれない。
- ブラウザの「画像をコピー」も HTML と画像が同居するため、同じくテキストが優先される。
- ファイルマネージャによってはテキスト形式を公開せず、`⌘V` のイベント自体が届かない。
- arboard の Linux 実装は画像データを `image/png` でしか要求しない。

# Decision

画像ペーストの経路を、クリップボードのテキストに依存しない形へ広げる。

1. `Event::Paste(text)` が来たら、まず `text/uri-list` / 素のパスを解析し、実在する
   画像ファイルを読み込む。`file://` のパーセントデコード、CRLF、コメント行、
   複数ファイルの URI リストに対応する。
2. テキストが HTML のときは、テキストと画像が同居している可能性が高いので、
   arboard でクリップボードを直接読み、画像データを拾う。
3. ツールバー右端に「ペースト」ボタンを常設し、`⌘⇧V` にも同じ動作を割り当てる。
   どちらも arboard で直接読み、画像データ → ファイルリスト → テキスト中のパスの順に探す。
   `⌘V` と違い、egui のイベント生成を迂回できる。
4. 読み込む形式は image クレートで PNG / JPEG / GIF / WebP / BMP。
5. arboard は `image-data` と `wayland-data-control` を有効にして使う。
   失敗時は通知に表示し、stderr に形式ごとの診断を出す（無言で失敗しない）。

不採用: egui-winit のクリップボード処理を無効化して `⌘V` を自前実装する案
（テキスト入力欄へのコピー＆ペーストまで壊れる）、macOS だけの固定対応
（Linux が主対象）、画像形式ごとに外部コマンドを呼ぶ案（配布が壊れる）。

# Consequences

## Pros

- Linux のファイルマネージャからコピーした画像ファイルを、`⌘V` または「ペースト」で取り込める。
- テキストと画像が同居するブラウザ等でも、ボタン・`⌘⇧V` なら画像を取れる。
- どの形式で失敗したかを stderr と通知で確認できる。

## Cons

- `⌘V` は依然として egui-winit のイベント生成に依存するため、テキスト形式を公開しない
  クリップボードでは「ペースト」ボタンか `⌘⇧V` を使う必要がある。
- arboard の画像取得は Linux では PNG のみ。JPEG 等しか提供しないクリップボードでは、
  ファイルパスが取れない限りまだ取り込めない。
- ツールバーにボタンが1つ増え、既定の 1100pt 幅では2段に折り返す。
- クリップボードの読み取りは UI スレッドで行うため、所有者の応答が遅いと一瞬止まる。
